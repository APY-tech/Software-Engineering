## 一、总体策略

需求有 19 条、设计图有 6 张，一次性让模型"写一个二手交易系统"必然得到一堆
无法核对的大文件。实际采用的是**按模块切分、先规约后实现、每轮都跑检查**的
方式：

1. 每轮只喂一个模块的输入：相关需求条目原文 + 对应的 UML 片段 + 已有代码
   的接口签名；
2. 要求模型先给出**方法签名与前置/后置条件**（存根 + 规约），我确认后再让它
   填实现；
3. 每轮结束立刻跑 `compileall`、`pylint`、`pytest`，把报错原文贴回下一轮；
4. 模型产出的每一行都读过，改动写进 git 提交说明（标注 AI 生成 / 人工修改）。

## 三、模型生成不符合预期的具体案例

### 案例 1：审核服务漏掉"审核期间被预约"的状态

- **现象**：演示脚本第 7 节给已发布商品提交修改、买家预约、管理员通过，抛
  `Conflict: 商品当前为已预约，不在待审核状态`。
- **原因**：模型按"审核只发生在 AUDITING 或 PUBLISHED"写分支，但 REQ-017 明确
  允许修改审核期间买家继续预约，商品会变成 `RESERVED`，此时待审内容仍应能通过。
- **处理**：把可挂待审内容的状态抽成 `_REVISION_HOLDERS = (PUBLISHED, RESERVED,
  CONFIRMED)`，`approve/reject/pending` 三处共用；补测试
  `test_revision_can_be_approved_after_reservation`。

### 案例 2：交易完成只通知卖家

- **现象**：`test_auto_finish_after_seven_days` 失败——买家收件箱没有完成通知。
- **原因**：模型把"完成"当成卖家关心的事件；REQ-015 原文要求"自动完成并通知买家"。
- **处理**：`_finish` 同时给买卖双方发通知，测试保留（测试是对的，代码是错的）。

### 案例 3：把"必填校验"放在建草稿时

- **现象**：需求要求"草稿保存成功""必填字段缺失时不能提交"，模型初稿在
  `create_draft` 就强制描述非空，导致无法保存未写完的草稿。
- **处理**：`_validate_fields(strict)` 分两档，建草稿只校验标题/价格/分类，
  提交审核时再查描述；演示脚本第 2 节把这个过程打出来。

### 案例 4：编解码函数被 pylint 判为 `too-many-return-statements`

- **现象**：`_decode_value` 有 7 个 return。
- **处理**：改成"先解 Optional，再按分支给 `result` 赋值"的单一出口写法，
  而不是加 `# pylint: disable`。

## 四、人工审查要点

- 逐轮读过全部代码，重点核对：状态迁移是否与状态图一致、权限判断是否每个
  写操作都有、异常信息是否能指导用户下一步操作。
- 对模型给的每条"看起来对"的规则，都在演示脚本或测试里造一个反例去撞它，
  撞不过就说明规则是假的。上面 4 个案例都是撞出来的。
- 拒绝了两类生成结果：一是把业务规则写进实体方法的版本（规则会散落在实体里，
  且事务边界不清）；二是用 `# pylint: disable` 消警告的版本。
